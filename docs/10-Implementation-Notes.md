# 10 — 实现说明与技术取舍

## 1. 为什么本版不是 Spring Boot + Vue

此前产品方案建议正式 SaaS 使用 Java 21 + Spring Boot + Vue 3。为了让这份交付在没有 Maven、Node、Docker 和外网下载依赖的环境里也能**直接启动并验证**，本版采用：

- Java 21 JDK 内置 `HttpServer` 提供 API。
- 原生 HTML / CSS / JavaScript 提供演示界面。
- JDK 内置文件 API 保存本地 JSON 数据。

它的目标是可执行的业务流程样机，不是要替代最终生产技术架构。这样能避免交付一个由于依赖下载或数据库环境缺失而无法启动的工程。

## 2. 继续产品化时的推荐迁移

建议保持业务概念和 API 语义，重构为：

- 后端：Spring Boot 3.5 + Java 21，按模块化单体组织。
- 数据库：PostgreSQL，使用 Flyway 管理 schema。
- 前端：Vue 3 + TypeScript + Vite + Element Plus。
- 认证：Spring Security / OIDC 或成熟身份服务。
- 异步：先用 DB outbox + worker；确认吞吐瓶颈后再引入消息系统。
- AI：Provider-neutral Model Gateway，模型密钥仅保存在服务端。

## 4. 规则评分为什么不是 AI

当前评分是透明可复现的字段完整性规则，便于验证 UI、API 和业务流程。它没有训练数据，也没有统计学概率校准，因此不能用“AI 已判断该客户成交概率为 86%”等话术展示。

正式 AI 评分需要：

1. 明确评分目标和业务标签（如有效商机、成交、无效线索）。
2. 建立脱敏的历史标注数据和时间切分测试集。
3. 测试不同市场/行业的偏差和准确性。
4. 输出依据、未知项和置信度。
5. 保留人工纠正与反馈机制。
6. 监控漂移和模型成本。

## 5. 已知技术限制

- 单实例、单工作空间；并发写入依赖 JVM 同步，不适合多节点。
- JSON 整体重写；数据量增大后必须迁移关系型数据库。
- 没有完善日志系统、请求追踪和性能指标。
- 没有生产级身份校验和跨租户安全测试。
- 未经授权不得将当前应用放到公网接受真实客户数据。
